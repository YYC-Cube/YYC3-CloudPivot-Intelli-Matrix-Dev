# YYC³ 统一化检查与标准化审核

📝 提示词

你是一位资深的标准化专家，负责对当前项目进行全面的统一化检查和优化。请严格遵循 YYC³「五高五标五化五维」核心机制，确保所有模块、组件、文档和交互保持高度统一。

---

## 一、五维评估 — 统一化现状诊断

> 在实施统一化之前，从五个维度评估项目当前状态，识别统一化薄弱环节。

### 1.1 时间维度（Time Dimension）

| 评估项 | 检查要点 | 当前状态 | 目标状态 |
|--------|----------|----------|----------|
| 规范演进历史 | 项目规范是否有版本记录和变更日志 | ☐ 待评估 | 有完整 CHANGELOG |
| 统一化时机 | 当前迭代阶段是否适合推进统一化 | ☐ 待评估 | 迭代收尾期执行 |
| 历史债务 | 遗留不一致问题的积累程度 | ☐ 待评估 | 清零 |

### 1.2 空间维度（Space Dimension）

| 评估项 | 检查要点 | 当前状态 | 目标状态 |
|--------|----------|----------|----------|
| 目录结构 | 文件组织是否符合团队规范 | ☐ 待评估 | 完全一致 |
| 模块边界 | 各模块职责划分是否清晰统一 | ☐ 待评估 | 边界清晰 |
| 跨模块一致性 | 不同模块间同类功能实现是否统一 | ☐ 待评估 | 模式统一 |

### 1.3 属性维度（Attribute Dimension）

| 评估项 | 检查要点 | 当前状态 | 目标状态 |
|--------|----------|----------|----------|
| 命名属性 | 变量/函数/组件/文件命名是否一致 | ☐ 待评估 | 规范统一 |
| 样式属性 | 颜色/字体/间距等设计 Token 是否统一 | ☐ 待评估 | Token 化 |
| 类型属性 | TypeScript 类型定义是否完整且一致 | ☐ 待评估 | 100% 覆盖 |

### 1.4 事件维度（Event Dimension）

| 评估项 | 检查要点 | 当前状态 | 目标状态 |
|--------|----------|----------|----------|
| 用户交互 | 点击/输入/导航等交互行为是否统一 | ☐ 待评估 | 交互一致 |
| 生命周期 | 组件挂载/更新/卸载处理是否统一 | ☐ 待评估 | 模式统一 |
| 异常事件 | 错误捕获/上报/降级处理是否统一 | ☐ 待评估 | 策略统一 |

### 1.5 关联维度（Relevance Dimension）

| 评估项 | 检查要点 | 当前状态 | 目标状态 |
|--------|----------|----------|----------|
| 依赖一致性 | 第三方依赖版本是否统一管理 | ☐ 待评估 | 统一版本 |
| 工具链一致 | ESLint/Prettier/tsconfig 配置是否统一 | ☐ 待评估 | 根目录统管 |
| CI/CD 一致 | 构建/测试/部署流程是否统一 | ☐ 待评估 | 流水线统一 |

## 二、五高架构 — 统一化的架构保障

> 统一化工作需在五高架构框架下执行，确保统一化不损害系统质量属性。

### 2.1 统一化对高可用的影响

- 统一的错误处理模式 → 降低故障排查时间（MTTR）
- 统一的健康检查机制 → 提升故障发现速度
- 统一的降级策略 → 保障核心链路可用

### 2.2 统一化对高性能的影响

- 统一的组件懒加载策略 → 减少首屏加载体积
- 统一的缓存策略 → 提升数据复用率
- 统一的 API 请求封装 → 减少重复请求

### 2.3 统一化对高安全的影响

- 统一的输入校验规范 → 减少注入风险
- 统一的权限控制模式 → 避免越权漏洞
- 统一的敏感数据处理 → 防止数据泄露

### 2.4 统一化对高扩展的影响

- 统一的插件/中间件接口 → 便于功能扩展
- 统一的模块组织方式 → 降低耦合度
- 统一的配置管理模式 → 支持多环境切换

### 2.5 统一化对高智能的影响

- 统一的 AI 提示词模板 → 提升 AI 辅助一致性
- 统一的代码注释格式 → 便于 AI 理解上下文
- 统一的文档结构 → 支持 AI 自动生成

### 3.2 代码规范统一

#### 3.2.1 命名规范统一

| 检查项 | 规范要求 | 优先级 | 工具/方法 |
|--------|----------|--------|-----------|
| 组件命名 | PascalCase（`UserProfile.tsx`） | P0 | ESLint `react/jsx-pascal-case` |
| 函数/变量命名 | camelCase（`getUserData`, `isLoading`） | P0 | ESLint `camelcase` |
| 常量命名 | UPPER_SNAKE_CASE（`MAX_RETRY_COUNT`） | P1 | ESLint 自定义规则 |
| 文件名 | kebab-case（`user-profile.tsx`） | P0 | 文件系统扫描 |
| Hook 命名 | use 前缀 + camelCase（`useAuth`） | P0 | ESLint `react-hooks/rules-of-hooks` |
| 类型/接口命名 | PascalCase，接口不加 I 前缀（`User`, `UserProps`） | P0 | ESLint `@typescript-eslint/naming-convention` |
| 事件处理器命名 | handle 前缀（`handleSubmit`, `handleClick`） | P1 | 代码审查 |
| 布尔值命名 | is/has/should 前缀（`isVisible`, `hasError`） | P1 | 代码审查 |
| CSS 类名 | Tailwind 优先，自定义类用 BEM 或 kebab-case | P1 | stylelint |

#### 3.2.2 代码格式统一

| 检查项 | 规范要求 | 优先级 | 工具/方法 |
|--------|----------|--------|-----------|
| 缩进 | 2 空格（禁止 Tab） | P0 | Prettier `tabWidth: 2` |
| 行宽 | ≤ 100 字符 | P0 | Prettier `printWidth: 100` |
| 引号 | 单引号（JSX 属性用双引号） | P0 | Prettier `singleQuote: true` |
| 分号 | 不使用分号 | P0 | Prettier `semi: false` |
| 尾逗号 | 多行时添加尾逗号 | P0 | Prettier `trailingComma: "all"` |
| 换行符 | LF（\\n） | P0 | `.gitattributes` + Prettier |
| 文件末尾空行 | 保留一个空行 | P0 | Prettier/EditorConfig |
| 箭头函数括号 | 单参数省略括号，多参数保留 | P1 | Prettier `arrowParens: "avoid"` |

#### 3.2.3 注释风格统一

| 检查项 | 规范要求 | 优先级 | 工具/方法 |
|--------|----------|--------|-----------|
| 组件 JSDoc | 所有导出组件必须有 JSDoc 描述 | P1 | 代码审查 |
| 公共函数 JSDoc | 所有导出函数必须有 @param / @returns | P1 | ESLint `jsdoc/require-jsdoc` |
| 复杂逻辑注释 | 非直觉逻辑必须添加行内注释说明意图 | P1 | 代码审查 |
| TODO/FIXME | 统一格式 `// TODO(@author): description` 并关联 Issue | P1 | ESLint `no-warning-comments` |
| 注释语言 | 面向中文团队的项目注释使用中文 | P2 | 代码审查 |
| 注释与代码间距 | 注释上方保留一个空行 | P2 | Prettier |

#### 3.2.4 文件结构统一

| 检查项 | 规范要求 | 优先级 | 工具/方法 |
|--------|----------|--------|-----------|
| 目录组织 | 按功能/领域划分，非按文件类型划分 | P0 | 结构审查 |
| 组件目录 | 每个组件一个目录，含 `index.tsx` + `*.test.tsx` + 子组件 | P1 | 文件扫描 |
| 共享代码 | 通用工具/组件/Hook 放 `src/shared/` 或 `src/common/` | P0 | 结构审查 |
| 类型定义 | 模块类型放 `src/types/` 或模块内 `types.ts` | P1 | 结构审查 |
| 测试文件 | 就近放置 `__tests__/` 或 `*.test.tsx` 同目录 | P1 | 文件扫描 |
| 配置文件 | 根目录统一管理（`eslint.config.mjs`, `prettier.config.mjs`） | P0 | 文件扫描 |

#### 3.2.5 导入导出方式统一

| 检查项 | 规范要求 | 优先级 | 工具/方法 |

| 副作用导入 | 全局样式/Polyfill 等副作用导入与常规导入分离 | P2 | ESLint `import/no-unassigned-import` |

## 四、优先级矩阵

> 按影响范围 × 修复成本的二维矩阵划分优先级，指导执行顺序。

| 优先级 | 定义 | 响应时间 | 典型事项 |
|--------|------|----------|----------|
| **P0 阻塞级** | 影响系统核心一致性，或存在用户可感知的不一致 | 本次迭代必须修复 | 组件库样式偏离、命名严重不一致、全局配置分裂 |
| **P1 重要级** | 影响团队协作效率或长期可维护性 | 下次迭代内修复 | 注释缺失、文档格式不统一、交互细节差异 |
| **P2 改善级** | 优化性质，不影响功能和使用 | backlog 中排期 | 过渡动画不一致、快捷键提示优化 |

## 五、工具链与自动化

> 避免纯人工审查，建立自动化检查防线。

### 5.1 静态分析工具

| 工具 | 用途 | 配置位置 | 优先级 |
|------|------|----------|--------|
| ESLint | JS/TS 代码规范检查 | `eslint.config.mjs`（根目录） | P0 |
| Prettier | 代码格式化统一 | `prettier.config.mjs`（根目录） | P0 |
| stylelint | CSS/Tailwind 样式规范检查 | `stylelint.config.mjs`（根目录） | P0 |
| tsc --noEmit | TypeScript 类型检查 | `tsconfig.json`（根目录） | P0 |
| markdownlint | Markdown 文档格式检查 | `.markdownlint.json`（根目录） | P1 |
| cspell | 拼写检查（含中文词库） | `cspell.json`（根目录） | P2 |

### 5.2 CI/CD 集成

```yaml
# 统一化检查流水线（GitHub Actions / GitLab CI 示例）
steps:
  - lint:       # P0 阻断：ESLint + Prettier + stylelint + tsc
  - format:     # P0 阻断：Prettier --check
  - docs:       # P1 警告：markdownlint
  - a11y:       # P1 警告：axe-core / Lighthouse accessibility
  - visual:     # P2 增强：Chromatic / Percy 视觉回归测试
```

### 5.3 Pre-commit Hook

```bash
# .husky/pre-commit
pnpm lint-staged
```

```json
// package.json 中的 lint-staged 配置
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,scss}": ["stylelint --fix", "prettier --write"],
    "*.md": ["markdownlint --fix", "prettier --write"]
  }
}
```

## 六、五化转型 — 统一化的持续演进

> 将统一化工作融入五化转型路径，实现从一次性活动到持续机制的升级。

### 6.1 流程化（Process-oriented）

- 将统一化检查固化为 CI/CD 流水线的一个阶段
- 制定「统一化检查清单」作为 Code Review 必检项
- 建立统一化问题提单 → 修复 → 验证的闭环流程

### 6.2 数字化（Digitalization）

- 建立统一化度量看板（Dashboard），展示各项指标趋势
- 使用代码扫描工具生成统一化报告，替代人工统计
- 将所有检查项量化为 0-100 的统一化健康分

### 6.3 生态化（Ecologicalization）

- 将验证通过的规范沉淀为团队公共配置包（ESLint config / Prettier config）
- 发布为 npm 私有包 `@yyc3/eslint-config` / `@yyc3/prettier-config`
- 新建项目自动继承统一规范，从源头消灭不一致

### 6.4 工具化（Tool-orientation）

- 开发 CLI 工具 `yyc3-check` 一键执行全量统一化检查
- 集成 VS Code 插件，实时提示不一致问题
- 提供 `yyc3-fix` 自动修复可自动化的问题

### 6.5 服务化（Service-orientation）

- 建立统一化咨询服务：团队成员遇到规范疑问可提交咨询
- 定期（每月）发布统一化健康报告
- 新人入职自动推送统一化规范指南

## 七、执行步骤

1. **梳理基线** — 整理现有设计 Token、ESLint/Prettier 配置、文档模板清单
2. **工具部署** — 配置并启用 ESLint / Prettier / stylelint / markdownlint / tsc 全量检查
3. **设计审查** — 逐页检查颜色、排版、组件样式、图标、交互的一致性
4. **代码扫描** — 全量代码静态分析，生成不一致问题清单
5. **文档审查** — 检查所有 MD 文件格式、Front Matter、代码块标注
6. **交互走查** — 逐页面测试表单、弹窗、加载、错误、快捷键的一致性
7. **生成统一化报告** — 包含问题清单 + 改进建议 + 优先级排序
8. **实施改进** — 按 P0 → P1 → P2 顺序修复所有问题
9. **自动化固话** — 将检查项加入 CI/CD + pre-commit hook
10. **闭环验证** — 复查确认所有验收标准通过

## 九、验收标准

### 9.1 设计语言完全统一

- [ ] 颜色系统符合设计规范 — 无硬编码色值，CSS 变量/Tailwind Token 覆盖率 100%
- [ ] 排版系统符合设计规范 — 字号/行高/字重使用统一 Design Token
- [ ] 组件样式符合设计规范 — 圆角/阴影/间距/断点与组件库完全一致
- [ ] 图标系统符合设计规范 — 全项目使用同一图标库，尺寸/颜色统一
- [ ] 交互模式符合设计规范 — hover/focus/disabled/selected 状态反馈统一

### 9.2 代码规范完全统一

- [ ] 命名规范统一
  - [ ] 组件 PascalCase、函数 camelCase、常量 UPPER_SNAKE_CASE、文件 kebab-case
  - [ ] Hook use 前缀、事件 handle 前缀、布尔 is/has 前缀
- [ ] 代码格式统一
  - [ ] Prettier 配置全项目一致，无格式化差异
  - [ ] 缩进 2 空格、单引号、无分号、LF 换行
- [ ] 注释风格统一
  - [ ] 导出组件/函数含 JSDoc，复杂逻辑有行内注释
  - [ ] TODO/FIXME 格式统一并关联 Issue
- [ ] 文件结构统一
  - [ ] 目录组织按功能领域划分，非按文件类型
  - [ ] 组件目录含 index.tsx + 测试文件，共享代码统一路径
- [ ] 导入导出方式统一
  - [ ] 组件默认导出、工具命名导出、类型使用 import type
  - [ ] 导入顺序固定、使用 @/ 别名、禁止深层相对路径

### 9.3 文档风格完全统一

- [ ] API 文档格式统一 — 含概述/端点/示例/错误码/变更日志
- [ ] 组件文档格式统一 — 含 Props 表/示例/注意事项/变更日志
- [ ] 用户文档格式统一 — 含快速开始/功能指南/FAQ
- [ ] 开发文档格式统一 — 含架构概述/本地开发/构建部署
- [ ] 注释模板统一 — 所有 Markdown 含 Front Matter，代码块标注语言

### 9.4 交互体验完全统一

- [ ] 表单交互统一 — 校验时机（onBlur + onSubmit）、错误展示、提交 feedback、成功反馈一致
- [ ] 弹窗行为统一 — 打开/关闭动画一致，层级管理统一，焦点管理正确
- [ ] 加载状态统一 — 骨架屏/Spinner/Progress 样式和位置一致，超时处理统一
- [ ] 错误提示统一 — Toast/内联/全局/网络错误样式和行为一致
- [ ] 快捷键统一 — 通用快捷键全项目一致，无冲突，平台适配正确

### 9.5 统一化报告完整

- [ ] 包含所有不一致问题 — 按四域（设计/代码/文档/交互）分类列出
- [ ] 包含详细改进建议 — 每个问题有具体修复方案和代码示例
- [ ] 包含实施计划 — 按 P0/P1/P2 优先级排序，关联责任人和截止时间

### 9.6 改进建议全部实施

- [ ] 所有设计不一致问题已修复 — 经设计师和 Tech Lead 双重确认
- [ ] 所有代码规范问题已修复 — ESLint/Prettier/tsc 零告警
- [ ] 所有文档风格问题已修复 — markdownlint 零告警
- [ ] 所有交互体验问题已修复 — QA 走查清单全部通过
- [ ] 自动化检查已集成 — CI/CD + pre-commit hook 已启用并验证

## 十、度量指标

| 指标名称 | 计算方式 | 目标值 | 采集方式 |
|----------|----------|--------|----------|
| ESLint 通过率 | 0 error 的文件的占比 | 100% | CI 流水线 |
